# hermes-rex

A [Hermes Agent](https://github.com/NousResearch/hermes-agent) plugin that makes
Hermes aware of the [Rex](https://www.superlogical.com/rex) terminal.

When Hermes runs inside a Rex pane it:

- **Reports its state to Rex** with the
  [Program Status Protocol (OSC 7501)](https://www.superlogical.com/rex/docs/build/program-status):
  working (with the current tool), blocked (permission, question or auth, with the
  reason), done (first line of the reply) and error. Rex shows these in the tab bar
  and session picker and sends its Done notification.
- **Tells the model where it is**: a system prompt section with the session's
  `REX_SESSION` and `REX_BLOCK` ids and how to use the `rex` CLI, generated by
  `rex __internal session-start` so it always matches the installed Rex.
- **Registers the `rex` skill** (`rex:rex`), the same stub `rex skill setup`
  installs for Claude Code and Codex: the model loads the full, version-matched
  CLI guide on demand.

## Install

    hermes plugins install vanhoof/hermes-rex
    hermes plugins enable rex

That is all. Start a new Hermes session (CLI or `hermes --tui`) inside a Rex
pane. To check the wiring from inside a pane:

    hermes rex doctor

### Optional: exact mode

By default the plugin finds the pane from Hermes's own per-session traces
(fallback mode, see below). Forwarding the pane ids into each session is more
direct, and also puts `REX_SESSION` and `REX_BLOCK` in the terminal tool's
environment. Either run

    hermes rex doctor --fix

or add to `~/.hermes/config.yaml`:

```yaml
terminal:
  client_env_passthrough: ["REX_BLOCK", "REX_SESSION", "REX_SERVER", "REX_BIN_DIR"]
```

## Demo and smoke test

From inside a Rex pane, with the plugin enabled:

    scripts/demo.sh            # full run, closes the Hermes pane at the end
    scripts/demo.sh --keep     # leave the Hermes pane open
    scripts/demo.sh --tui      # use the Hermes TUI instead of the classic CLI
    scripts/demo.sh --no-question   # skip the clarify step
    scripts/demo.sh --no-split      # skip the step where Hermes splits its own pane

It opens Hermes in a pane to the right with a live status monitor below it,
asks Hermes where it runs, asks it to pose a question so Rex shows the blocked
state and answers it, then has Hermes open a pane below the demo with the rex
CLI, run `uptime` there, read the output back and close it. The demo pane
prints the Rex status records as they change and ends with a summary. Record
the window to show the whole flow.

## Settings

In `~/.hermes/config.yaml` under `plugins.entries.rex.settings`:

| key              | default  | meaning |
|------------------|----------|---------|
| `session_naming` | `false`  | let the model rename the Rex session after its task |
| `app_label`      | `hermes` | the `app` id in status reports |
| `debug`          | `false`  | write a hook trace to `<plugin data dir>/debug.log` |

## How it works

Hermes runs every CLI and TUI turn in its gateway daemon, so plugin hooks fire
in a process with no terminal. The plugin maps each session to its pane's tty:

1. **Exact mode**: the forwarded client environment names the Rex pane; the
   plugin asks Rex which process the pane runs and uses that process's tty.
2. **Fallback mode**, no configuration:
   - classic CLI: Hermes's terminal breadcrumbs (`~/.hermes/terminal-sessions`)
     map a tty to its session id;
   - TUI: each TUI front end carries the path of its active-session file in its
     environment; the file holds the session id and `ps` gives the tty. Exact
     for any number of TUIs;
   - last resort: the single running TUI's tty.
   The Rex ids for the context block are then read from the environment of a
   process on that tty, since every process in a Rex pane inherits them.

Status reports are written straight to the tty. Nothing is written to stdout.
Sessions that did not come from a terminal (Telegram, Discord, cron, ...) are
ignored.

## What the plugin runs

Subprocesses: `rex` (block lookup, session-start text, `whoami` in the doctor)
and `ps` (tty of a pid). No network access. No credentials read.

## Limits

- In exact mode Hermes freezes a session's client environment when the session
  is created, so a session resumed in a different pane reports to the original
  pane until a new session starts (hermes-agent #146211). Fallback mode follows
  the breadcrumbs and so tracks a resume.
- The sudo password prompt is drawn by the client and raises no hook, so it
  does not show as blocked. Approvals and clarifying questions do.
- One private seam: `agent.session_client_env.bound_client_env` (in-tree, not a
  public plugin API; hermes-agent #141194 asks for one). Guarded: if it changes,
  exact mode is skipped and fallback mode still works.
